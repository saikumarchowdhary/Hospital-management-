Prompt 1, the full build:

Build CareLine, an original Hospital Management System for iPhone in SwiftUI with a real backend (Supabase). It is ONE app with two experiences: the Patient mobile app and the Hospital Staff portal (role shells). Roles: Patient, Doctor, Nurse, Receptionist, Case Manager, Laboratory Staff, Pharmacist, Accountant, Administrator, HR/Hiring, Publisher/Approver, External Coordination Requester/Approver, plus Housekeeping Supervisor, Housekeeping Staff and Candidate (job applicant). Role permissions are configurable (module, action, data scope) and every role gets least privilege. Its own name, logo and words, all below. Today is Tuesday, November 24, 2026. All names, dates, amounts, counts and providers are SAMPLE data and must be labelled as sample in the UI.

Shared patient journey the app must support end to end: Discover (search doctors/services) → Register → Book (slot check, hold, no duplicates) → Confirm/pay → Receive care (encounter, investigations, treatment) → Access records → Follow up (reminders, refills, next appointment). Cross-cutting on every module: identity verification, consent, role-based access, notifications, audit history, payment reconciliation.

STATUS FLOW AND RULES
Only the transitions below exist (transition tables in Domain/Workflow.swift mirrored in the Postgres functions; anything else is rejected). Every transition writes its history entry, notification(s) and audit row in one database transaction.
- Appointment: Pending payment → Confirmed → Checked in → Completed; Cancelled, Failed, No-show, Rescheduled (per configured windows). A slot can never be double-booked (unique constraint plus hold with expiry).
- Payment: Pending → Paid / Failed / Cancelled; Paid → Refunded. Idempotent by transaction reference.
- Lab order: Ordered → Scheduled → Collected → In analysis → Result entered → Reviewed → Released.
- Refill: Submitted → Pending → Approved / Rejected.
- Ambulance request: Submitted → Received → Assigned → Updated → Closed (Received/Assigned only set by the dispatch user).
- Admission: Registered → Bed allocated → Admitted → Discharge pending → Discharged. Bed: Available → Occupied → Cleaning → Ready → Available.
- Notice: Draft → Pending approval → Approved / Changes requested / Rejected → Published → Expired. Campaign: Draft → Submitted → Approved → Scheduled/Published → Paused / Cancelled / Expired.
- Vacancy: Draft → Pending approval → Published → Closed. Application: Submitted → Under Review → Shortlisted → Interview Scheduled → Selected / Not Selected.
- External request (all five categories): Draft → Submitted → Approval pending → Provider processing → Confirmed → Fulfilled → Closed; exceptions Rejected, Unavailable, Delayed, Cancelled, Escalated.
- Purchase: Draft → Approval pending → PO created → Dispatched → Received → Invoice matched. Housekeeping: Assigned → In Progress → Awaiting inspection → Completed (or Reopened). Insurance case: Eligibility checked → Pre-auth submitted → Query → Approved / Rejected → Claim submitted → Settled. Blood issue: Reserved → Compatibility checked → Authorized → Issued. Staffing: Requested → Approved → Credentials verified → Deployed → Closed.
Rules: patients see only their own data; clinical, financial, HR/candidate, insurance and payroll permissions are separate; dosage cannot be altered by patients; dispensing cannot exceed stock without an authorized exception; no blood unit is issued without authorization and traceability; no clinical deployment before credential checks; PO needs approval; a room is not Ready before inspection passes; closed vacancies, expired notices and expired campaigns stop automatically; availability data always carries source and last-updated time. Payment credentials stay with the provider; never store raw card data. Emergency access must never be obstructed by promotions. Every financial change is attributed and auditable.
